## Purpose

`tx doc` manages structured documentation as first-class primitives. In practice, that means PRDs and design docs live as markdown files on disk with YAML frontmatter and embedded YAML blocks. Docs are `.md` files in `specs/` with metadata and links stored in the database. This enables:

- **Structured PRDs** with stable fields, lifecycle state, linked references, and mandatory EARS requirements
- **Version-controlled docs** that live alongside code
- **Linked doc graphs** connecting overviews, PRDs, and design docs
- **Markdown-first authoring** — prose and metadata in a single `.md` file, no generation pipeline
- **Derived spec rules** from docs for traceability and closure

## EARS in tx PRDs

tx uses **EARS** (**Easy Approach to Requirements Syntax**) as the standard requirement format for PRDs. EARS requirements are defined as embedded YAML blocks within the markdown body.

Why EARS is mandatory:

- Plain bullet requirements are ambiguous and untestable.
- EARS gives requirements a predictable structure that is machine-parseable and lintable.
- EARS IDs map cleanly to test cases in DD testing strategies (traceability).
- tx validates EARS early with `tx spec lint` before implementation starts.
- EARS-structured invariants populate provenance fields for full traceability.

EARS requirements use the `REQ-<SCOPE>-NNN` ID format with markdown-native clause fields plus a `statement` field for the action clause:

| Kind | Sentence Pattern |
|------|-----------------|
| `ubiquitous` | The system shall ... |
| `event-driven` | `when: <trigger>` + `statement: the system shall ...` |
| `state-driven` | `while: <state>` + `statement: the system shall ...` |
| `optional` | Where \<feature\>, the system shall ... |
| `unwanted` | If \<condition\>, then the system shall ... |
| `complex` | Combination of When/While/If/Where clauses |

- Required clause fields are `when` for `event-driven`, `while` for `state-driven`, `if` for `unwanted`, and `where` for `optional`.
- `complex` requires at least one of `when`, `while`, `if`, or `where`.
- `statement` should contain only the action clause, such as `the authentication service shall issue tokens`.
- Legacy decomposed EARS using `pattern:` and underscored values such as `event_driven` is supported only for backward compatibility and migration.

## Spec Types

Docs use `kind: spec` with a `spec_type` field in frontmatter:

| spec_type | Purpose |
|-----------|---------|
| `prd` | Product Requirements Document (scope, acceptance criteria) |
| `design` | Design Document (technical specification) |
| `overview` | Project-level overview (one per project) |
| `runbook` | Operational procedures (symptoms, diagnosis, mitigation) |
| `decision` | Architecture Decision Records (ADRs) |

Docs now have an immutable `doc_id` in frontmatter and the database. The human `name` slug only needs to be unique within its doc kind, so `prd/auth` and `design/auth` can coexist without suffix conventions.

## Lifecycle

Docs have these statuses:

```
draft → review → approved → locked
```

- **draft**: initial authoring, can be updated freely
- **review**: under review, pending approval
- **approved**: accepted spec, active and authoritative
- **locked**: immutable, must create a new version to make changes

## Usage

<Tabs groupId="interface" persist items={["CLI", "TypeScript SDK", "MCP", "REST API"]}>
<Tab value="CLI">

```bash
# Create docs (generates markdown template with frontmatter)
tx doc add prd auth-system-prd --title "Authentication System PRD"
tx doc add design auth-system-design --title "Authentication System Design"
tx doc link auth-system-prd auth-system-design
tx doc add overview system-overview --title "System Overview"

# Edit a doc (opens markdown in $EDITOR)
tx doc edit auth-system-prd

# Show doc metadata
tx doc show auth-system-prd

# Show doc source markdown
tx doc show auth-system-prd --md

# List all docs
tx doc list
tx doc list --kind prd
tx doc list --status draft

# Remove latest mutable doc version
tx doc rm auth-system

# Lock a doc (makes it immutable)
tx doc lock auth-system

# Create a new version (doc must be locked first)
tx doc version auth-system

# Link two docs
tx doc link system-overview auth-system-prd

# Attach a task to the PRD/DD pair
tx doc attach tx-abc123 auth-system-prd --type implements
tx doc attach tx-abc123 auth-system-design --type references

# Create a design patch
tx doc patch auth-system-design auth-patch-001 "Fix auth flow"

# Run all doc/spec checks (drift, EARS, coverage, spec-test status)
tx spec lint
tx spec lint --json
```

## Markdown Structure

Docs are stored as markdown files in `specs/` with YAML frontmatter and embedded YAML blocks:

```
specs/
  system-design.md            # Overview
  prd/
    auth-system.md            # PRD
    data-pipeline.md
  design/
    auth-design.md            # Design doc
    auth-patch-001.md         # Design patch
  system-design/
    error-handling.md          # System design
  index.md                    # Documentation index
```

Example PRD markdown:

````markdown
---
kind: spec
spec_type: prd
name: auth-system
title: Authentication System
status: draft
version: 1
owners:
  - auth-team
summary: JWT-based authentication for user login
domain: auth
tags:
  - auth
  - security
depends_on: []
supersedes: []
implements: null
last_reviewed_at: 2026-03-15
---

# Summary

JWT-based authentication system for user login.

# Problem

Users cannot log in to the application.

# Scope

Included: registration, login, password reset
Excluded: OAuth, SSO

# Requirements

```yaml
ears_requirements:
  - id: REQ-AUTH-001
    kind: event-driven
    when: a user submits valid credentials
    statement: the authentication service shall issue access and refresh tokens
    priority: must
    rationale: core login success path
```

# Acceptance Criteria

```yaml
acceptance_criteria:
  - id: AC-001
    statement: Users can register and log in
  - id: AC-002
    statement: Tokens expire after 15 minutes
  - id: AC-003
    statement: Refresh token rotation works
```

# Non-goals

- OAuth/SSO integration
- Multi-factor authentication
````

## Index Searchability

tx builds `specs/index.md` from doc frontmatter. Three fields determine whether
PRDs and design docs stay easy to find later:

- `summary`: becomes the Description column in `specs/index.md`
- `domain`: contributes subsystem terms to Search Keywords
- `tags`: contributes additional Search Keywords

This metadata is enforced as part of doc linting. `tx spec lint` warns when:

- `summary` is missing or still templated,
- `domain` is missing or still a placeholder,
- `tags` are missing or only generic values.

Use subsystem-specific wording so agents can find the right spec by feature
area, domain term, or implementation concern.

Example:

```yaml
summary: Transactional auth token issuance for login and refresh flows
domain: auth
tags:
  - auth
  - tokens
  - refresh
  - session-management
```

Use `tx spec lint` to validate EARS requirement compliance.
