## Purpose

Keep requirements and technical designs beside the code as Markdown files in
`specs/`. tx stores their identity, metadata and links in SQLite.

## Commands

```bash
tx doc add prd checkout-prd --title "Checkout requirements"
tx doc add design checkout-design --title "Checkout design"
tx doc link checkout-prd checkout-design
tx doc list
tx doc show checkout-design --md
tx doc sync checkout-design
tx spec lint
```

Edit the generated file while preserving its frontmatter. Use `doc_id`, `kind/name`
or an unambiguous name to reference a document. Run `tx doc --help` for versions,
locking, task attachments and removal.

## Workflow

Start with a design and an implementation plan. Add a PRD when a separate
user-facing contract helps define the work.
PRD requirements use EARS: a trigger or state plus an observable action. For example:

```yaml
ears_requirements:
  - id: REQ-CHECKOUT-001
    kind: event-driven
    when: a customer retries a completed payment
    statement: the system shall return the existing order
    priority: must
```

Design [invariants](./invariants) define what must remain true in the code. Preserve
the generated sections and use `tx spec lint` to catch schema and section issues.
The four built-in document kinds are `prd`, `design`, `overview` and `plan`; projects
can configure other kinds. Sync your edits with `tx doc sync`, then lock reviewed
documents before creating a new version:

```bash
tx doc sync checkout-design
tx doc lock checkout-design
tx doc version checkout-design
tx doc show checkout-design --doc-version 1 --md
```

A new version keeps the previous locked source in `specs/.versions/` and leaves the
current editable Markdown at its usual path. Commit both paths. Repository-wide
`tx doc sync` updates working documents and skips locked history. Versions created
before v0.20 may share their original source path; tx cannot reconstruct past
content that was already overwritten.

Save your coding agent's [plan](./plans), link the specification to it, then create
[task](./tasks) attachments: **spec -> plan -> tasks**. Use [tx spec](./spec-trace)
to map invariants and record executed test evidence. REST, MCP and SDK access are
listed on [Interfaces](../interfaces).
